    SEC.02

    How Many Repositories Do You Need?

    Recommendation: polyrepo (one repo per service) + 3 shared/infra repos. This is the real production pattern — not a monorepo — because teams deploy independently and CI/CD stays scoped per service.

    01 · finclient-api-gateway
    Spring Cloud Gateway, routing, rate limiting
    02 · finclient-auth-service
    OAuth2/JWT integration layer, Keycloak config
    03 · finclient-user-service
    User profiles, accounts
    04 · finclient-payment-service
    Core transaction/payment logic
    05 · finclient-notification-service
    Email/SMS/push, Kafka consumer
    06 · finclient-audit-logging-service
    Compliance/event log store
    07 · finclient-common-libs
    Shared DTOs, exception handlers — published as an internal artifact, never copy-pasted
    08 · finclient-infra
    Terraform/CloudFormation, EKS cluster config
    09 · finclient-helm-charts
    Helm charts for all services
    10 · finclient-ci-templates
    Reusable GitHub Actions workflows
    Minimum viable set for learning solo: repos 01, 03, 04, 07, 08 — five repos. Add the rest as the project grows; don't create ten repos on day one, that's how side projects die from ops overhead.

    Alternative: a single monorepo with /services/* folders, split into polyrepo once it gets real. Simpler CI early, painful access-control/git-blame later — document that tradeoff if you choose it.

    SEC.03

    Microservices Breakdown

    finclient/
├── api-gateway            → single entry point, routing, auth token relay
├── auth-service            → wraps Keycloak, issues/validates JWTs
├── user-service            → user CRUD, profile, KYC data
├── payment-service         → transactions, ledger, idempotency
├── notification-service    → Kafka consumer → email/SMS/push
└── audit-service           → immutable event log, compliance

    Each service owns its own PostgreSQL schema — no shared DB across services — and talks to others only via REST (sync) or Kafka events (async), never direct DB access. Every service exposes /actuator/health and /actuator/prometheus.

    SEC.05

    Cross-Cutting Concerns

    5.1 — JWT + OAuth2

    • Run Keycloak as your Identity Provider (self-hosted, or AWS Cognito if you want managed).
    • Each microservice is a Spring Security OAuth2 Resource Server — validates JWT signature/claims only, doesn't issue tokens.
    • Gateway does coarse-grained auth (is the token valid?); each service does fine-grained authorization via @PreAuthorize.
    • Short-lived access tokens (~15 min) + refresh tokens.

    5.2 — Caching (Redis)

    • Use spring-boot-starter-data-redis with @Cacheable / @CacheEvict.
    • Cache read-heavy, rarely-changing data — user profiles, config.
    • Also use Redis for rate limiting at the gateway and distributed locks.

    5.3 — Logging

    • Structured JSON logging (logback + logstash-logback-encoder) — never plain text in production.
    • Include traceId/spanId in every log line for correlation with tracing.
    • Ship logs via Promtail → Loki, visualize alongside metrics in Grafana.
    • Never log PII or secrets — mask account numbers, tokens.

    5.4 — Messaging: Kafka vs RabbitMQ

    Recommendation: Kafka, given the fintech-style domain.

    • Kafka: high throughput, event replay, log-based — fits payment/audit domains well.
    • RabbitMQ: simpler, better for task-queue/RPC-style messaging, lower ops overhead.
    • Use Kafka for domain events (payment created, user registered) in v1 — don't run both at once, that's infra sprawl for a learning project.

    5.5 — Resilience

    Resilience4j on every inter-service HTTP call: circuit breaker, retries with backoff, bulkheads to isolate thread pools per downstream dependency.

    SEC.06

    Database Strategy

    • One PostgreSQL instance/schema per service (database-per-service pattern) — enforces service boundaries.
    • Flyway migrations versioned in each service's own repo, under src/main/resources/db/migration.
    • RDS Multi-AZ in AWS, or the CloudNativePG operator if self-managing Postgres in K8s.
    • No cross-service joins. For aggregated data, build a read model via Kafka events (CQRS-lite) or query each service's own API.
    SEC.07

    Folder Structure (per microservice)

    Package-by-feature layout — scales better than package-by-layer:

    payment-service/
├── src/main/java/com/finclient/payment/
│   ├── PaymentServiceApplication.java
│   ├── config/                  → SecurityConfig, KafkaConfig, RedisConfig, OpenApiConfig
│   ├── transaction/              → feature module
│   │   ├── Transaction.java              (entity)
│   │   ├── TransactionRepository.java
│   │   ├── TransactionService.java
│   │   ├── TransactionController.java
│   │   ├── dto/
│   │   │   ├── TransactionRequest.java
│   │   │   └── TransactionResponse.java
│   │   └── mapper/TransactionMapper.java
│   ├── ledger/                   → another feature module (same pattern)
│   ├── event/                    → Kafka producers/consumers
│   │   ├── PaymentEventProducer.java
│   │   └── PaymentEventListener.java
│   ├── exception/
│   │   ├── GlobalExceptionHandler.java
│   │   └── custom exceptions
│   └── common/                   → shared internal utils (not the shared lib)
├── src/main/resources/
│   ├── application.yml
│   ├── application-dev.yml
│   ├── application-prod.yml
│   └── db/migration/             → Flyway scripts (V1__init.sql, V2__add_index.sql)
├── src/test/java/...              → unit + integration tests (mirror main structure)
├── Dockerfile
├── docker-compose.yml             → local dev only (Postgres, Redis, Kafka)
├── helm/                          → Helm chart for this service
│   ├── Chart.yaml
│   ├── values.yaml
│   ├── values-prod.yaml
│   └── templates/
├── .github/workflows/ci-cd.yml
├── pom.xml (or build.gradle)
└── README.md

    Rules of thumb:

    • Controllers stay thin — validate, then delegate to the service.
    • Services hold business logic, never touch HttpServletRequest.
    • Repositories are Spring Data JPA interfaces only — no business logic.
    • DTOs in, DTOs out — never expose JPA entities directly over REST.
    • MapStruct for entity↔DTO mapping to avoid manual boilerplate.
    SEC.08

    Containerization & Local Dev

    Each service ships a multi-stage Dockerfile — build stage with Maven/Gradle, runtime stage on a slim JRE image (e.g. eclipse-temurin:21-jre-alpine). A root-level docker-compose.yml spins up Postgres, Redis, Kafka, and Keycloak locally so real AWS is never required for day-to-day development.

    SEC.09

    Kubernetes Layout

    Namespaces:
  finclient-dev
  finclient-staging
  finclient-prod

Per namespace:
  Deployment + Service + HPA (autoscaling) per microservice
  ConfigMap (non-secret config)
  Secret (DB creds, API keys — synced from AWS Secrets Manager via External Secrets Operator)
  Ingress → routes to API Gateway
  ServiceMonitor (Prometheus scrape config)
    • Helm charts (one per service, or one umbrella chart) for repeatable deployments.
    • HPA tied to CPU/memory or custom metrics.
    • Readiness/liveness probes pointing to Spring Actuator health endpoints.
    SEC.10

    CI/CD Pipeline (per service repo)

    1. Push/PR       → trigger GitHub Actions
2. Build         → mvn/gradle build
3. Test          → unit + integration tests (Testcontainers for Postgres/Kafka)
4. Static checks → SonarQube/SonarCloud, dependency scan (Snyk/Trivy)
5. Build image   → Docker build, tag with git SHA
6. Push image    → AWS ECR
7. Deploy        → ArgoCD detects new tag (GitOps) → syncs to EKS
                    (or: GitHub Actions runs `helm upgrade` directly for something simpler)
8. Post-deploy   → smoke test / synthetic check

    Environment promotion: dev (auto-deploy on merge to main) → staging (manual approval) → prod (manual approval).

    SEC.12

    Best Practices Checklist

    • 12-factor config — env vars/ConfigMaps, never hardcoded
    • Stateless services — session state in Redis, not memory
    • Idempotent APIs for payment-critical endpoints
    • Automated, versioned DB migrations (Flyway)
    • No secrets in git — ever
    • API versioning — /api/v1/...
    • Global exception handler — RFC 7807 Problem Details
    • Input validation via jakarta.validation
    • Rate limiting at the gateway
    • Correlation IDs propagated across service calls
    • Contract testing between services (Spring Cloud Contract / Pact)
    • Unit + integration (Testcontainers) + a few E2E tests
    • Blue/green or canary deploys (Argo Rollouts)
    • Documented backup / disaster-recovery plan
    SEC.13

    Suggested Build Order (Learning Path)

    Single service firstBuild user-service fully — CRUD + Postgres + tests — before touching microservices complexity.
    Add authWire up Keycloak + JWT resource server on that one service.
    Containerize itDockerfile, docker-compose with Postgres.
    Add a second servicepayment-service, connected via REST — now the microservices tradeoffs become real.
    Add Kafkapayment-service publishes an event, notification-service consumes it.
    Add an API GatewayIn front of both services.
    Add Redis cachingTo one hot endpoint.
    Add observabilityActuator + Prometheus + Grafana, then Loki for logs, then tracing.
    Containerize everythingWrite Helm charts, deploy to local K8s (kind/minikube) first.
    Set up CI/CDGitHub Actions for build/test/push, then ArgoCD for GitOps deploy.
    Move to AWS EKS lastOnce the whole stack already works locally in Kubernetes.

    This order matters: it means you're never debugging Kubernetes, Kafka, and OAuth2 all at once — each new concept lands on a working foundation.
