Redis Deep Dive

What Redis is, why it exists, its core data structures, persistence and eviction model, messaging and scripting capabilities, clustering, real-world use cases, and Spring Boot integration.

1. What Is Redis?

Redis (Remote Dictionary Server) is an open-source, in-memory data structure store used as a database, cache, message broker, and streaming engine. Unlike traditional databases that treat data as rows in tables, Redis exposes data as native structures — strings, hashes, lists, sets, sorted sets, streams — and lets applications operate on them directly and atomically.

It was created by Salvatore Sanfilippo in 2009 to solve a specific problem: relational databases were too slow for the read-heavy, low-latency workloads modern web apps needed. Redis trades some durability guarantees for speed, keeping the full dataset in RAM while optionally persisting it to disk.

In-Memory Execution

Data operations reside entirely in RAM, delivering sub-millisecond latencies for read/write workloads.

Single-Threaded Event Loop

Uses I/O multiplexing (epoll/kqueue) to serve requests sequentially, avoiding lock contention and race conditions entirely.

2. Core Features

Atomic Operations

Every command (including compound ones like INCR or LPUSH) executes atomically — no partial writes, no manual locking.

Rich Data Types

Strings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLogs, and geospatial indexes — not just key/value blobs.

Persistence Options

RDB snapshots, AOF logs, or both together — tunable durability vs. performance tradeoff.

Pub/Sub Messaging

Built-in publish/subscribe channels for real-time fan-out messaging between services.

Replication & HA

Master-replica replication, automatic failover via Sentinel, and horizontal sharding via Redis Cluster.

Lua Scripting

Server-side scripts run atomically, letting you bundle multi-step logic into a single round trip.

TTL & Eviction

Per-key expiration and configurable eviction policies make Redis a natural fit as a bounded cache.

Transactions

MULTI/EXEC queues commands and runs them as one atomic, isolated unit.

3. Essential Data Structures

Strings

Binary-safe values up to 512MB. Used for session caching, counters (INCR), and general key-value pairs.

Hashes

Field-value pairs representing objects (e.g., user:1001 -> {name, email}). Memory-efficient via ziplists.

Lists

Ordered, doubly-linked collections. Power job queues and activity feeds via LPUSH/RPOP.

Sets

Unordered, unique elements. Used for tagging, deduplication, and set algebra (SINTER, SUNION).

Sorted Sets (ZSETs)

Unique elements ordered by floating-point score. Backed by skip lists; ideal for leaderboards and rate limiters.

Streams

Append-only log structure with consumer groups — a lightweight alternative to Kafka for event pipelines.

Bitmaps

Bit-level operations over strings. Extremely compact for feature flags, daily active user tracking.

HyperLogLog

Probabilistic structure estimating cardinality (unique counts) using ~12KB regardless of dataset size.

4. Persistence Mechanisms: RDB vs AOF

RDB (Redis Database Snapshot)

Point-in-time snapshots created at set intervals via fork(). Fast recovery; minor data loss risk on sudden crashes.

AOF (Append Only File)

Logs every write command received. Near real-time durability with configurable sync (fsync everysec).

In production, most teams enable both: AOF for durability, with periodic RDB snapshots for fast full restores and backups.

5. Eviction Policies & TTL

When Redis reaches its maximum configured RAM limit (maxmemory), it applies eviction policies:

  • volatile-lru / allkeys-lru: Removes Least Recently Used keys.
  • volatile-lfu / allkeys-lfu: Removes Least Frequently Used keys.
  • volatile-ttl: Removes keys with the shortest remaining TTL first.
  • volatile-random / allkeys-random: Removes a random key.
  • noeviction: Returns memory errors when full — writes fail, reads still succeed.

6. Pub/Sub & Streams for Messaging

Redis supports two messaging models with different guarantees:

Pub/Sub

Fire-and-forget. Messages published to a channel go only to currently connected subscribers — nothing is stored, so offline consumers miss messages.

Streams

Durable, ordered logs with consumer groups. Multiple consumers can each track their own read position, enabling replay and load-balanced processing.

PUBLISH orders:created '{"orderId": 4471}'
SUBSCRIBE orders:created

XADD orders:stream '*' orderId 4471 status CREATED
XREADGROUP GROUP order-workers consumer-1 COUNT 10 STREAMS orders:stream '>'

7. Transactions & Lua Scripting

Redis transactions queue commands with MULTI and run them atomically with EXEC — no other client's commands can interleave. For conditional logic, Lua scripts go further: the entire script runs as a single atomic step server-side.

MULTI
INCR inventory:sku_42
DECRBY wallet:user_9 500
EXEC

-- Lua: atomic check-then-decrement, avoids race conditions
EVAL "
  local stock = tonumber(redis.call('GET', KEYS[1]))
  if stock > 0 then
    redis.call('DECR', KEYS[1])
    return 1
  end
  return 0
" 1 inventory:sku_42

8. Spring Boot Caching with Redis

Spring Boot provides a declarative AOP caching framework using annotations mapped to Redis:

@Service
@RequiredArgsConstructor
public class ProductService {
    private final ProductRepository repo;

    // Cache Hit checks Redis first; Cache Miss executes method and populates Redis
    @Cacheable(value = "products", key = "#id", unless = "#result == null")
    public Product getProduct(Long id) {
        return repo.findById(id).orElseThrow();
    }

    // Forces method execution and updates Redis entry
    @CachePut(value = "products", key = "#product.id")
    public Product updateProduct(Product product) {
        return repo.save(product);
    }

    // Evicts stale entry from Redis
    @CacheEvict(value = "products", key = "#id")
    public void deleteProduct(Long id) {
        repo.deleteById(id);
    }
}

Direct Access with RedisTemplate

For cases that need more than annotation-based caching — counters, sorted sets, pub/sub — RedisTemplate gives direct command access:

@Service
@RequiredArgsConstructor
public class RateLimiterService {
    private final StringRedisTemplate redisTemplate;

    public boolean isAllowed(String userId, int limit, Duration window) {
        String key = "rate:" + userId;
        Long count = redisTemplate.opsForValue().increment(key);
        if (count != null && count == 1) {
            redisTemplate.expire(key, window);
        }
        return count != null && count <= limit;
    }
}

9. High Availability & Clustering

Replication

Asynchronous master-replica replication lets reads scale horizontally while writes stay on the master.

Redis Sentinel

Provides high availability with automatic failover and monitoring for master-replica setups.

Redis Cluster

Provides horizontal scaling by sharding keys across 16,384 hash slots across multiple master nodes.

Client-Side Routing

Cluster-aware clients compute the hash slot for a key and route requests to the correct node directly.

11. Performance Notes & Common Pitfalls

avoid KEYS * watch for hot keys pipeline batch ops size big values carefully
  • Never use KEYS * in production — it blocks the single event loop while scanning the whole keyspace. Use SCAN instead, which iterates incrementally.
  • Pipeline round trips. Sending 100 commands one-by-one costs 100 network round trips; pipelining batches them into one.
  • Watch key size. A single massive hash or list can dominate memory and slow operations on that key — shard large collections across multiple keys where possible.
  • Hot keys skew cluster load. Because Redis Cluster shards by key hash, one extremely popular key can overload a single node regardless of overall cluster capacity.
  • Set TTLs deliberately. Caches without expiry silently become permanent storage and can exhaust maxmemory.
