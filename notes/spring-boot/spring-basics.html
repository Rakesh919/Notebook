Spring Basics

The foundational concepts that everything else in Spring is built on: the IoC container, beans, their lifecycle, scopes, configuration styles, and AOP.

1. Inversion of Control (IoC)

IoC is the principle underneath all of Spring: instead of your code creating and managing its own dependencies (new SomeService()), you hand that responsibility to a container. The container "inverts" who's in control — your objects no longer control their own construction, the framework does.

Dependency Injection (covered in its own note) is simply how the IoC container delivers dependencies once it's in control.

2. The IoC Container

The container is the engine that reads your bean definitions, creates objects, wires their dependencies, and manages their full lifecycle. Spring provides two flavors:

ContainerWhat It Is
BeanFactoryThe basic, lightweight container interface — lazy-loads beans only when requested. Rarely used directly today.
ApplicationContextThe container Spring Boot actually uses. Extends BeanFactory with eager loading, event publishing, internationalization, and AOP support.

3. What Is a Bean?

A bean is simply an object whose creation and lifecycle are managed by the Spring container, rather than by your own code. Any class can become a bean once it's registered with the container — either by annotation or by explicit configuration.

Stereotype Annotations

@Component

The generic stereotype — marks any class as a Spring-managed bean, discovered via component scanning.

@Service

Semantically marks a class as holding business logic. Functionally identical to @Component, but signals intent.

@Repository

Marks a data-access class. Spring also translates database exceptions into its own DataAccessException hierarchy for beans marked this way.

@Controller

Marks a class as a Spring MVC web controller, whose methods handle incoming HTTP requests.

All four are really just @Component under the hood, given a more specific name so both developers and the framework can reason about a class's role at a glance.

4. Configuring Beans: Three Approaches

Component Scanning

Annotate your own classes with a stereotype annotation; Spring finds them automatically by scanning packages.

Java Config

@Configuration class with @Bean methods — used for third-party classes you can't annotate, or when construction needs custom logic.

XML Config

The original approach (<bean> tags in an XML file). Still supported for legacy compatibility, essentially unused in new Spring Boot projects.

@Configuration
public class AppConfig {

    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper()
            .registerModule(new JavaTimeModule());
    }
}

@SpringBootApplication  // includes @ComponentScan — turns on scanning automatically
public class ShopApplication {
    public static void main(String[] args) {
        SpringApplication.run(ShopApplication.class, args);
    }
}

5. Bean Scopes

ScopeLifetime
singleton (default)One shared instance per Spring container, reused everywhere it's injected.
prototypeA brand-new instance is created every time the bean is requested.
requestOne instance per HTTP request (web apps only).
sessionOne instance per user's HTTP session (web apps only).
applicationOne instance per ServletContext — effectively singleton, scoped to the whole web app.
@Component
@Scope("prototype")
class ReportBuilder {
    // a new ReportBuilder is created every time it's injected or requested
}

6. The Bean Lifecycle

Spring drives every bean through a well-defined sequence of steps from creation to destruction:

1. Instantiate       — constructor is called
2. Populate          — dependencies are injected
3. @PostConstruct    — custom init logic runs (if defined)
4. Bean is ready     — available for use by the application
5. @PreDestroy       — custom cleanup logic runs on container shutdown
@Component
class CacheWarmer {

    @PostConstruct
    public void warmUp() {
        // runs once, right after dependency injection completes
    }

    @PreDestroy
    public void cleanUp() {
        // runs once, right before the container shuts the bean down
    }
}

7. Aspect-Oriented Programming (AOP)

AOP lets you apply cross-cutting concerns — logging, security checks, transaction handling — declaratively, without cluttering business logic with repeated boilerplate.

Aspect

A module containing cross-cutting logic (e.g., a logging aspect).

Advice

The actual code that runs — @Before, @After, or @Around a method call.

Pointcut

An expression defining which methods the advice applies to.

Join Point

A specific point during execution — typically a method call — where advice can be applied.

@Aspect
@Component
class LoggingAspect {

    @Around("execution(* com.shop.service.*.*(..))")
    public Object logExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        Object result = joinPoint.proceed();
        long duration = System.currentTimeMillis() - start;
        System.out.println(joinPoint.getSignature() + " took " + duration + "ms");
        return result;
    }
}

The most common real-world use of AOP in Spring is one you've likely already used without writing any AOP code yourself: @Transactional is implemented as an aspect that wraps your method in a database transaction, committing on success and rolling back on exception.

8. Profiles

Profiles let you register beans or apply configuration only in certain environments — dev, test, prod — from the same codebase.

@Configuration
@Profile("dev")
class DevMailConfig {
    @Bean
    public MailClient mailClient() {
        return new FakeMailClient(); // logs to console instead of sending real email
    }
}

Activated via application.properties (spring.profiles.active=dev) or an environment variable at startup — no code changes needed to switch environments.

9. Quick Reference

  • IoC is the principle; the container (ApplicationContext) is what implements it.
  • A bean is any object the container creates and manages — marked via a stereotype annotation or declared via @Bean.
  • Default bean scope is singleton; reach for prototype only when you genuinely need a fresh instance each time.
  • @PostConstruct/@PreDestroy hook into the bean lifecycle for setup/teardown logic.
  • AOP is what powers @Transactional and similar "invisible" cross-cutting behavior.
