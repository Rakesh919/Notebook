Spring Bean Lifecycle — Complete Deep Dive

The exhaustive, senior-level architectural guide to the Spring Bean Lifecycle: from Classpath Component Scanning, BeanDefinition Registration, Instantiation, and Aware Interception to BeanPostProcessors, Proxy Creation, and Destruction Handlers.

1. Introduction & Purpose

A Spring Bean is an object that is instantiated, assembled, managed, and destroyed by the Spring Inversion of Control (IoC) container. Unlike plain Java objects created using the new operator (where memory management and initialization are strictly controlled by the developer), Spring-managed beans undergo a rigorous, deterministic lifecycle.

Why Does the Bean Lifecycle Exist?

The lifecycle gives developers hook points to intercept bean creation at precise phases. This allows running custom validation, injecting environment metadata, wrapping objects in AOP dynamic proxies, establishing external connection pools, and releasing OS resources cleanly upon context shutdown.

Container Responsibilities

The Spring IoC container acts as an orchestrator. It manages dependency resolution, lifecycle phase callbacks, scope storage (Singleton, Prototype, Request, Session), and shutdown hooks without leaking framework code into domain entities.

Core Architecture Principle:
Spring decouples class instantiation from initialization. Instantiation creates the raw Java heap object via reflection or constructors; Property Population wires dependencies; Initialization executes domain-specific startup logic and applies cross-cutting concerns (such as AOP proxies for @Transactional or @Async).

3. Step-by-Step Lifecycle Execution

Let's examine each phase of the lifecycle in depth:

Phase 1: Bootstrapping & Metadata Parsing

During startup, ClassPathBeanDefinitionScanner uses ASM bytecode reading to parse target .class files without initializing classes in the JVM. It wraps parsed class metadata into a BeanDefinition object and registers it inside the BeanDefinitionRegistry.

Phase 2: Instantiation & Dependency Injection

The container instantiates the raw bean via reflection or constructor invocation. Immediately after, AutowiredAnnotationBeanPostProcessor scans and injects required dependencies into fields, setters, or constructors.

Phase 3: Aware Interception

If the bean implements any Spring Aware interfaces, Spring injects internal container infrastructure references before initialization.

Phase 4: Initialization Callbacks & Proxying

Spring executes three distinct initialization callbacks in strict sequential order:

  1. @PostConstruct (Processed by InitDestroyAnnotationBeanPostProcessor)
  2. InitializingBean.afterPropertiesSet()
  3. Custom initMethod configured in @Bean

Finally, AnnotationAwareAspectJAutoProxyCreator executes postProcessAfterInitialization() to generate CGLIB or JDK dynamic proxies for classes requiring transactional, caching, or security aspects.

Phase 5: Teardown & Destruction

When the application context shuts down, destruction callbacks execute in strict reverse order:

  1. @PreDestroy
  2. DisposableBean.destroy()
  3. Custom destroyMethod

4. BeanFactoryPostProcessor Mechanics

A BeanFactoryPostProcessor (BFPP) operates on the BeanDefinition metadata before any bean instances are created on the heap. This allows modifying configuration parameters, reading external property files, or adding dynamic bean definitions programmatically.

@Component
public class CustomMetadataModifier implements BeanFactoryPostProcessor {

    @Override
    public void postProcessBeanFactory(ConfigurableListableBeanFactory beanFactory) 
            throws BeansException {
        
        BeanDefinition bd = beanFactory.getBeanDefinition("orderService");
        // Dynamically force OrderService to be lazily initialized
        bd.setLazyInit(true);
    }
}
Critical Difference:
BeanFactoryPostProcessor modifies Bean Definitions (blueprints).
BeanPostProcessor modifies Bean Instances (created heap objects).
Never inject standard beans into a BeanFactoryPostProcessor class—doing so forces premature instantiation of those beans before BeanPostProcessors are ready, bypassing lifecycle callbacks!

5. BeanPostProcessor Deep Dive

BeanPostProcessor (BPP) is the core extension hook inside Spring. It intercepts every bean instance after property population, allowing custom modification or wrapping beans in proxy objects.

@Component
public class CustomProxyBeanPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) throws BeansException {
        // Runs before @PostConstruct and initMethod
        if (bean instanceof AuditAware) {
            ((AuditAware) bean).setAuditTimestamp(System.currentTimeMillis());
        }
        return bean;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) throws BeansException {
        // Runs after all initialization callbacks. Used for AOP Proxy generation.
        return bean;
    }
}

8. Aware Interfaces Mechanics

Spring's Aware interfaces act as marker callbacks allowing a bean to request a reference to container infrastructure objects. They run right before BeanPostProcessor pre-initialization.

Common Aware Interfaces
  • BeanNameAware: Injects the string ID assigned to the bean in the container.
  • BeanFactoryAware: Injects the owning BeanFactory container instance.
  • ApplicationContextAware: Injects the full ApplicationContext instance.
  • EnvironmentAware: Injects active environment profiles and property sources.
  • ResourceLoaderAware: Injects resource loaders for reading classpath/file assets.
@Component
public class ContainerAwareService implements BeanNameAware, ApplicationContextAware {
    private String beanName;
    private ApplicationContext context;

    @Override
    public void setBeanName(String name) {
        this.beanName = name;
    }

    @Override
    public void setApplicationContext(ApplicationContext context) {
        this.context = context;
    }
}

9. Singleton vs. Prototype Lifecycle

The scope of a bean completely alters how the Spring container manages its lifecycle:

Singleton Scope Lifecycle

Managed completely from birth to death by Spring. Instantiated once at startup, initialized, cached in singletonObjects, and destroyed cleanly when the context shuts down.

Prototype Scope Lifecycle

Spring instantiates, injects dependencies, and executes initialization callbacks (@PostConstruct, initMethod). However, Spring does NOT manage destruction for prototype beans. Once initialized, the instance is handed to the client, and the container forgets it.

Memory Leak Warning on Prototype Beans:
Because Spring does not track prototype instances after initialization, @PreDestroy and DisposableBean.destroy() will never be executed by Spring for prototype beans! If your prototype bean allocates heavy resources (e.g. database connections, file handles), the caller code must manage cleanup manually.

10. Internal Spring Classes Involved

The lifecycle is executed under the hood by these core internal Spring classes:

  • AbstractApplicationContext: Coordinates startup via refresh() and shutdown via close().
  • DefaultListableBeanFactory: Primary container map holding bean definitions and singleton object instances.
  • AbstractAutowireCapableBeanFactory: Executes the actual creation algorithms: createBean(), doCreateBean(), instantiateBean(), populateBean(), and initializeBean().
  • AutowiredAnnotationBeanPostProcessor: Processes @Autowired and @Value injections.
  • InitDestroyAnnotationBeanPostProcessor: Processes @PostConstruct and @PreDestroy annotations.
  • AnnotationAwareAspectJAutoProxyCreator: Creates CGLIB/JDK dynamic proxies during post-processing.

11. Real-World Production Example

Below is an enterprise-grade component demonstrating proper resource setup and teardown in a Redis connection pool manager:

@Component
public class RedisCacheManager implements BeanNameAware {
    private String beanName;
    private JedisPool jedisPool;

    @Override
    public void setBeanName(String name) {
        this.beanName = name;
    }

    @PostConstruct
    public void initPool() {
        System.out.println("Initializing Redis pool for bean: " + beanName);
        JedisPoolConfig config = new JedisPoolConfig();
        config.setMaxTotal(128);
        this.jedisPool = new JedisPool(config, "localhost", 6379);
    }

    public Jedis getResource() {
        return jedisPool.getResource();
    }

    @PreDestroy
    public void closePool() {
        System.out.println("Closing Redis connection pool...");
        if (jedisPool != null && !jedisPool.isClosed()) {
            jedisPool.close();
        }
    }
}

12. Performance & Startup Optimization

  • Minimize Heavy Work in @PostConstruct: Running blocking network calls or slow operations inside @PostConstruct freezes the entire application context startup thread. Offload slow initialization tasks to asynchronous threads or background events (e.g., ApplicationReadyEvent).
  • Avoid Unnecessary Post-Processors: Every registered BeanPostProcessor intercepts every single bean in the container. Complex logic inside custom BPPs drastically inflates boot times.
  • Spring AOT (Ahead-Of-Time): In Spring Boot 3, AOT pre-calculates component scanning, proxy generation, and bean definition registration at build time, eliminating dynamic reflection during startup.

13. Common Production Mistakes

1. Accessing Injected Dependencies in Constructors: Inside a constructor, field/setter injection has not happened yet! Referencing @Autowired fields inside a constructor throws a NullPointerException. Move initialization logic to @PostConstruct.

2. Self-Invocation of @PostConstruct Methods: Expecting manual initialization by calling init() explicitly bypasses Spring container state management.

3. Expecting @PreDestroy on Prototype Beans: As noted earlier, Spring does not track prototype instances post-initialization. Destruction callbacks will never fire for prototype beans.

14. Senior Best Practices

  • Prefer @PostConstruct / @PreDestroy: Use JSR-250 annotations for component classes to keep code decoupled from Spring interfaces.
  • Use @Bean(initMethod, destroyMethod) for 3rd Party Libraries: When registering external objects from third-party JARs, configure init/destroy callbacks inside the @Bean annotation.
  • Register Shutdown Hooks: In non-web standalone Spring applications, explicitly invoke context.registerShutdownHook() to ensure @PreDestroy handlers run on JVM termination.

15. 50+ Senior Interview Questions

Q1: What is the exact execution order of initialization callbacks in Spring?
1. Methods annotated with @PostConstruct
2. InitializingBean.afterPropertiesSet()
3. Custom initMethod configured in @Bean
Q2: What is the exact execution order of destruction callbacks in Spring?
1. Methods annotated with @PreDestroy
2. DisposableBean.destroy()
3. Custom destroyMethod configured in @Bean
Q3: Why shouldn't heavy initialization logic be placed inside a bean's constructor?
Inside a constructor, dependency injection has not taken place yet. All @Autowired fields and setters are null. Furthermore, constructors cannot be intercepted by BeanPostProcessors or proxied by AOP.
Q4: What is the difference between BeanFactoryPostProcessor and BeanPostProcessor?
BeanFactoryPostProcessor operates on BeanDefinition metadata before any beans are created. BeanPostProcessor operates on bean heap instances after instantiation and property population.
Q5: Does Spring manage the destruction lifecycle of Prototype-scoped beans?
No. Spring instantiates, injects dependencies, and runs initialization callbacks for prototype beans, but hands the instance to the caller and forgets it. Destruction callbacks like @PreDestroy are never executed by Spring for prototype beans.
Q6: Which BeanPostProcessor processes @PostConstruct and @PreDestroy annotations?
InitDestroyAnnotationBeanPostProcessor (or CommonAnnotationBeanPostProcessor).
Q7: Which BeanPostProcessor generates AOP dynamic proxies for @Transactional or @Async?
AnnotationAwareAspectJAutoProxyCreator (executing in postProcessAfterInitialization).
Q8: What happens if a @PostConstruct method throws a RuntimeException?
The ApplicationContext startup fails immediately, throwing a BeanCreationException and terminating initialization.
Q9: What are Aware interfaces in Spring?
Marker interfaces (e.g. BeanNameAware, ApplicationContextAware) that allow beans to request infrastructure references from the container.
Q10: When are Aware interface methods executed in the lifecycle?
Right after property population (dependency injection) and before BeanPostProcessor pre-initialization.
Q11: How to ensure @PreDestroy runs in a standalone desktop Spring app?
By calling ConfigurableApplicationContext.registerShutdownHook().
Q12: Can a @PostConstruct method be private or static?
It can be private, package-private, or public, but it MUST NOT be static.
Q13: Can a @PostConstruct method take arguments?
No. A @PostConstruct method must accept zero parameters.
Q14: What is the purpose of InitializingBean interface?
Provides afterPropertiesSet() to execute custom initialization after the container sets all bean properties.
Q15: Why is @PostConstruct preferred over InitializingBean?
It decouples application code from Spring-specific interfaces (JSR-250 standard).
Q16: What is BeanDefinition?
An internal metadata object describing a bean's class, scope, dependencies, and lifecycle methods before instantiation.
Q17: What is DefaultListableBeanFactory?
The default full-featured BeanFactory implementation holding bean definitions and singleton caches.
Q18: How does Spring avoid circular dependencies during initialization?
Using its Three-Level Cache (singletonObjects, earlySingletonObjects, singletonFactories) for setter/field injection loops.
Q19: What happens if two init methods are specified with identical names?
Spring deduplicates and executes the initialization logic once for that phase.
Q20: Can we have multiple @PostConstruct methods in a single class?
Yes, but the order of execution between multiple @PostConstruct methods in the same class is not guaranteed.
Q21: What is the role of PropertySourcesPlaceholderConfigurer?
It is a BeanFactoryPostProcessor that resolves ${...} placeholders in bean definitions.
Q22: Is @PostConstruct called on lazy singletons at container startup?
No. Lazy singletons are instantiated and initialized only when requested for the first time.
Q23: What is the default destroyMethod behavior in @Bean in modern Spring?
Modern Spring automatically infers and calls close() or shutdown() methods on third-party beans unless disabled using destroyMethod = "".
Q24: What is the purpose of DestructionAwareBeanPostProcessor?
A sub-interface of BeanPostProcessor that adds callbacks (requiresDestruction, postProcessBeforeDestruction) before a bean is destroyed.
Q25: What is the difference between Instantiation and Initialization?
Instantiation allocates memory and calls the constructor. Initialization populates properties, runs callbacks, and applies proxies.
Q26: What happens if a BeanPostProcessor returns null from postProcessBeforeInitialization?
Subsequent BeanPostProcessors are skipped, and the original bean instance is used as-is.
Q27: Which Spring internal class invokes createBean() and doCreateBean()?
AbstractAutowireCapableBeanFactory.
Q28: How does Spring process @PreDestroy on application shutdown?
During context closure, DisposableBeanAdapter runs registered destruction processors on singletons.
Q29: What is SmartInitializingSingleton?
A callback interface whose afterSingletonsInstantiated() method triggers after all non-lazy singletons are fully initialized.
Q30: How to control BeanPostProcessor execution order?
By implementing org.springframework.core.Ordered or using @Order.
Q31: What is the purpose of InstantiationAwareBeanPostProcessor?
Sub-interface of BPP allowing interception before instantiation (e.g. returning a custom proxy directly).
Q32: Can we call @Async methods inside @PostConstruct?
No! The AOP proxy that enables @Async is created in postProcessAfterInitialization, which runs after @PostConstruct. Calling it inside @PostConstruct executes it synchronously on the main startup thread.
Q33: Can a @Transactional method run properly inside @PostConstruct?
No! Similar to @Async, the transactional AOP proxy wrapper is created after @PostConstruct completes.
Q34: How to execute code safely after AOP proxies and all singletons are ready?
Listen for ContextRefreshedEvent or ApplicationReadyEvent using @EventListener.
Q35: What is MethodValidationPostProcessor?
A BeanPostProcessor that creates AOP proxies for beans annotated with @Validated.
Q36: What is the lifetime of a Request-scoped bean?
Created at the start of an HTTP request and destroyed when the HTTP request completes.
Q37: Does Spring run @PreDestroy on Request-scoped beans?
Yes, when the Servlet request completes, the web ApplicationContext destroys request-scoped beans cleanly.
Q38: What is MergedBeanDefinitionPostProcessor?
A BPP sub-interface used to post-process merged bean definitions (e.g. discovering @Autowired and @Value annotations).
Q39: What is the role of CustomScopeConfigurer?
A BeanFactoryPostProcessor used to register custom user-defined bean scopes in Spring.
Q40: Why should we avoid implementing InitializingBean and DisposableBean together?
It tightly couples domain components to Spring container interfaces without adding functional benefits over annotations.
Q41: What is the difference between SmartInstantiationAwareBeanPostProcessor and InstantiationAwareBeanPostProcessor?
Smart variant adds capabilities to predict bean types, determine candidate constructors, and retrieve early bean references.
Q42: Where are fully initialized singleton beans stored in Spring?
In the singletonObjects ConcurrentHashMap inside DefaultSingletonBeanRegistry.
Q43: What happens if custom init-method name specified in @Bean does not exist?
Spring throws a NoSuchMethodException wrapped inside a BeanCreationException during startup.
Q44: Can @PreDestroy methods throw checked exceptions?
They can, but exceptions thrown during shutdown are logged and swallowed so remaining singletons can shut down.
Q45: What is the primary advantage of Spring AOT in Boot 3 regarding lifecycle?
Eliminates dynamic reflection and classpath scanning during application startup.
Q46: How does Spring handle lifecycle callbacks for inherited superclasses?
Spring processes lifecycle annotations on superclasses first, then proceeds down the inheritance hierarchy.
Q47: What is ApplicationListener?
An interface/annotation mechanism to listen for container lifecycle events (e.g., startup, refresh, shutdown).
Q48: Does @Bean(initMethod) work for component-scanned classes?
No, initMethod is an attribute of the @Bean factory annotation, not @Component. Use @PostConstruct for components.
Q49: What is Lifecycle interface in Spring?
An interface (start(), stop(), isRunning()) for containers/beans managing background asynchronous tasks.
Q50: What is the ultimate architectural benefit of understanding the Spring Bean Lifecycle?
It empowers developers to extend framework capabilities, write custom infrastructure starters, prevent startup bugs, and optimize application performance.

16. Quick Revision Cheatsheet

BeanFactoryPostProcessor: Modifies Bean Definitions (Blueprints) BEFORE any beans are instantiated.

Bean Instantiation: Constructor execution allocates heap space for raw object.

Property Population: Field, setter, or constructor Dependency Injection.

Aware Callbacks: Injects container references (BeanNameAware, ApplicationContextAware).

BeanPostProcessor (Pre-Init): Executes @PostConstruct methods.

Initialization: Executes afterPropertiesSet() & custom initMethod.

BeanPostProcessor (Post-Init): Generates AOP Proxies (@Transactional, @Async).

Destruction Order: @PreDestroy → DisposableBean.destroy() → custom destroyMethod.
