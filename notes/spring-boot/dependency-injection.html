IoC & Dependency Injection

How Spring removes object instantiation boilerplate, manages dependencies at runtime, and keeps enterprise Java applications decoupled and testable.

1. What is Inversion of Control (IoC)?

In standard Java code, classes explicitly control the creation and wiring of their dependencies via new. With IoC, that responsibility is inverted: the control shifts from the class itself to an external framework container.

Traditional (Tight Coupling)

Class instantiates its own dependency: new OrderRepository(). Hard to mock or swap for testing.

With IoC (Decoupled)

Class declares what it needs via an interface. The container supplies it at startup.

2. IoC vs Dependency Injection (DI)

The two terms are often confused, but they are not the same thing:

  • IoC is the broad architectural principle ("Don't call us, we'll call you").
  • Dependency Injection (DI) is the specific design pattern Spring uses to deliver dependencies into your classes.

3. The 3 Types of Dependency Injection

Spring supports three ways to inject dependencies. Only one is recommended for day-to-day production code:

1. Constructor Injection (Recommended)

@Service
public class OrderService {
    private final OrderRepository orderRepository;

    // In modern Spring, @Autowired is optional on single constructors
    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}

Enables immutable fields (final), eliminates NullPointerException at runtime, and allows clean mock injection in plain JUnit tests without starting a Spring test context.

2. Setter Injection (Use for Optional Dependencies)

@Service
public class NotificationService {
    private AuditLogger auditLogger;

    @Autowired(required = false)
    public void setAuditLogger(AuditLogger auditLogger) {
        this.auditLogger = auditLogger;
    }
}

3. Field Injection (Avoid in Production)

@Service
public class UserService {
    @Autowired 
    private UserRepository userRepository; // Injected via reflection
}
Why avoid field injection? You cannot make fields final, you cannot instantiate the class manually in unit tests without reflection utilities, and it masks bloated classes hiding too many dependencies.

4. Visual Comparison: Constructor vs Setter Flow

1. Constructor Injection (Atomic Creation)

Dependencies are resolved first and passed directly into the constructor. The bean cannot exist in memory in a half-built state.

[OrderRepository] ────(passed into constructor)────> [OrderService(repo)]
                                                              │
                                                              ▼
                                                   [Fully Initialized Bean]
                                                   (fields can be final)
2. Setter Injection (Two-Phase Creation)

The raw bean is created first with a default constructor (fields are null). Later, the container calls setters to populate dependencies.

                                                  ▼
                                       [Populated Bean]
                                       (fields must be mutable)

5. Resolving Injection Conflicts: Multiple Candidates

When Spring finds more than one bean matching an interface, it throws a NoUniqueBeanDefinitionException unless you tell it which one to pick:

@Primary

Sets a default choice when no specific bean name is requested.

@Qualifier("beanName")

Targets an exact bean by name at the injection point.

@Service
public class NotificationSender {
    private final MessageService service;

    public NotificationSender(@Qualifier("smsService") MessageService service) {
        this.service = service;
    }
}

6. How the Container Works Under the Hood

You don't need to memorize internal Spring classes, but understanding the general startup pipeline helps debug configuration issues:

  1. Scan & Metadata: Spring scans your packages for classes annotated with @Component or methods with @Bean, converting them into internal BeanDefinition blueprints.
  2. Instantiation: The container creates bean instances by executing their constructors in dependency order.
  3. Property Population: Injected dependencies and properties (@Value) are supplied.
  4. Initialization: @PostConstruct methods and any custom init hooks execute.
  5. Proxy Creation: If a class uses features like @Transactional or @Async, Spring wraps the bean in an AOP proxy before saving it in the cache.

7. Circular Dependencies

A circular dependency occurs when Bean A requires Bean B, and Bean B simultaneously requires Bean A.

  • With Constructor Injection, Spring cannot instantiate either bean, throwing a BeanCurrentlyInCreationException immediately at startup.
  • Starting in Spring Boot 2.6+, circular references are prohibited by default.
  • The fix: Refactor your design. Circular dependencies almost always indicate poor separation of concerns. Extract shared functionality into a third service (Bean C).

8. Quick Summary

  • Always prefer Constructor Injection over field injection.
  • Keep beans stateless because singletons are shared across all incoming threads.
  • Use @Primary for defaults and @Qualifier for specific overrides.
  • Rely on @PostConstruct instead of putting complex startup setup inside your class constructor.
