Dependency Injection

The mechanism the IoC container uses to actually deliver dependencies into your objects.

The core idea

If IoC is the principle ("don't build your own dependencies"), DI is the implementation ("here's how the container hands them to you"). Spring supports three styles of injection.

StyleHowWhen Spring recommends it
ConstructorPassed into the constructorDefault choice — makes dependencies explicit and required
SetterSet via a setter methodOptional dependencies
Field@Autowired directly on a fieldConvenient, but harder to test — avoid in new code
Analogy: constructor injection is like a recipe that lists ingredients up front — you can't start cooking without them. Field injection is like grabbing ingredients out of the fridge mid-recipe: it works, but nobody can see what you actually needed just by reading the method. 
@Service
class OrderService {
    private final PaymentClient paymentClient;

    // Constructor injection — Spring supplies PaymentClient automatically
    OrderService(PaymentClient paymentClient) {
        this.paymentClient = paymentClient;
    }
}

Why constructor injection wins

It makes dependencies visible and mandatory, plays well with final fields, and makes unit testing trivial — you just pass a mock into the constructor, no Spring context required.
