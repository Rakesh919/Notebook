Spring IoC Container & Dependency Injection

The exhaustive, senior-level architectural guide to Spring's Inversion of Control container, 3-level singleton cache, ASM bytecode component scanning, BeanDefinition resolution, and enterprise production patterns.

1. Introduction

In traditional procedural and object-oriented Java applications, component classes explicitly control the creation, lifecycle, and assembly of their own dependencies. This tight coupling creates rigid codebases that are difficult to unit test, refactor, and scale.

What is Inversion of Control (IoC)?

Inversion of Control is a foundational architectural design principle wherein the control of object creation, configuration, and lifecycle management is inverted from the application code itself to an external framework or container runtime.

Problems in Traditional Java (Before IoC):
  • Tight Coupling: Classes instantiate concrete implementation dependencies directly using the new operator.
  • Testing Impediments: Mocking dependencies in isolated unit tests becomes impossible without refactoring production code.
  • Lifecycle Boilerplate: Every component must manually manage setup, thread-safety, singleton guarantees, and teardown logic.

Tight Coupling Code Example (Without IoC):

public class OrderService {
    // Direct instantiation creates high coupling to MySQLOrderRepository implementation
    private OrderRepository orderRepository = new MySQLOrderRepository();

    public void placeOrder(Order order) {
        orderRepository.save(order);
    }
}

Decoupled Code Example (With IoC Paradigm):

public class OrderService {
    private final OrderRepository orderRepository;

    // Control is inverted: Dependency is provided to the class from external container
    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    public void placeOrder(Order order) {
        orderRepository.save(order);
    }
}

2. What is the Spring IoC Container?

The Spring IoC Container is the core engine of the Spring Framework. It implements Inversion of Control by managing the entire lifecycle of application objects—from instantiation, dependency wiring, and post-processing, to scope management and final destruction.

1. Object Creation & Assembly

Instantiates classes via constructor, factory methods, or proxy factories based on configuration metadata.

2. Dependency Resolution

Inspects type requirements, auto-wires dependent beans, and constructs the runtime object graph.

3. Lifecycle Management

Executes lifecycle callbacks including aware interfaces, @PostConstruct, and @PreDestroy handlers.

4. Singleton & Scope Storage

Caches singletons in internal thread-safe registries and manages prototype/request custom scopes.

3. Internal Working of IoC Container

During application startup, the Spring container executes a structured sequence to transform configuration sources into a fully operational object graph.

1
Bootstrap & Component Scan: Container reads base packages defined by @ComponentScan or configuration classes.
↓
2
ASM Classpath Scanning: ClassPathBeanDefinitionScanner uses ASM bytecode readers to inspect .class files without loading them.
↓
3
BeanDefinition Registration: Parsed metadata is wrapped into BeanDefinition objects and stored in DefaultListableBeanFactory.
↓
4
BeanFactoryPostProcessor Execution: Custom post-processors (e.g., PropertySourcesPlaceholderConfigurer) modify metadata prior to object creation.
↓
5
Dependency Graph Construction & Instantiation: Non-lazy singletons are instantiated via constructor injection or reflection.
↓
6
Property Population & Dependency Injection: Dependencies are injected via setters, fields, or constructor arguments.
↓
7
BeanPostProcessor (Pre-Initialization): postProcessBeforeInitialization() runs (executing @PostConstruct methods).
↓
8
InitializingBean & Custom Init: afterPropertiesSet() and custom initMethod callbacks execute.
↓
9
BeanPostProcessor (Post-Initialization): postProcessAfterInitialization() wraps beans in AOP proxies if required.
↓
10
Ready Singleton: Bean is placed in the primary singleton cache (singletonObjects) for application use.

4. BeanDefinition Architecture

Spring does not directly instantiate objects upon reading class files. Instead, it first parses metadata into a BeanDefinition instance. A BeanDefinition serves as a detailed blueprint describing how a specific bean must be created, wired, and managed.

Stored Metadata Properties
  • Bean Class Name: Target concrete implementation class.
  • Scope: Singleton, Prototype, Request, etc.
  • Constructor & Property Values: Explicit configuration args.
  • Autowire Mode: byName, byType, constructor.
  • Lazy Init Flag: True/False initialization policy.
  • Init & Destroy Method Names: Defined lifecycle hooks.
// Conceptual internal representation of a BeanDefinition
public interface BeanDefinition {
    String getBeanClassName();
    String getScope();
    boolean isLazyInit();
    ConstructorArgumentValues getConstructorArgumentValues();
    MutablePropertyValues getPropertyValues();
    String[] getDependsOn();
}

5. BeanFactory vs ApplicationContext

Spring provides two core interfaces to represent the IoC container. BeanFactory is the basic root container interface, whereas ApplicationContext is an enterprise-grade extension that inherits from BeanFactory.

Feature BeanFactory ApplicationContext
Bean Initialization Lazy Loading (instantiates beans on getBean() request) Eager Loading (instantiates all non-lazy singletons at startup)
Enterprise Features Basic IoC & DI features only Adds AOP, i18n Internationalization, Event Publication, Environment Profiles
PostProcessor Auto-Registration Manual programmatic registration required Automatic detection and registration of BeanPostProcessor implementations
Spring Boot Usage Used as underlying bean storage layer Primary container interface used (e.g. ServletWebServerApplicationContext)

6. Dependency Injection Core Concept

Dependency Injection (DI) is the specific implementation mechanism of Inversion of Control whereby a component’s dependencies are "injected" into it by an external authority (the IoC container) rather than created internally.

Advantages of Dependency Injection:
  • Testability: Enables effortless substitution of real services with mock implementations during unit testing.
  • Loose Coupling: Dependencies are exposed via interfaces rather than concrete implementation classes.
  • Reusability: Components become modular and agnostic of their execution context or environmental bindings.

7. Types of Dependency Injection

Spring supports three primary mechanisms for injecting dependencies into components:

1. Constructor Injection (Recommended for Production)

@Service
public class PaymentService {
    private final PaymentGateway gateway;

    // @Autowired is optional on single constructors in modern Spring
    public PaymentService(PaymentGateway gateway) {
        this.gateway = gateway;
    }
}

2. Setter Injection (Recommended for Optional Dependencies)

@Service
public class NotificationService {
    private AuditLogger logger;

    @Autowired(required = false)
    public void setLogger(AuditLogger logger) {
        this.logger = logger;
    }
}

3. Field Injection (Not Recommended in Production)

@Service
public class UserService {
    @Autowired 
    private UserRepository userRepository; // Uses reflection directly
}
Injection Type Immutability Null Safety Ease of Unit Testing Circular Dependency Handling
Constructor Injection High (fields can be final) Guaranteed at instantiation time Excellent (pass mocks directly into constructor) Fails early at startup (prevents invalid graphs)
Setter Injection No (fields are mutable) Requires runtime null checks Good (call setters in test setup) Resolved via Early Singleton Exposure
Field Injection No (fields are mutable) Prone to NullPointerException Poor (requires ReflectionTestUtils or Spring runner) Hidden; masked until runtime issues arise

8. IoC vs Dependency Injection

Developers frequently conflate IoC and DI. However, IoC is an overarching architectural design principle, whereas Dependency Injection is one specific pattern used to implement IoC.

Real-World Analogy: The Car Factory

Without IoC: A Car object manufactures its own Engine, Wheels, and Transmission internally using its own tools.

With IoC (DI): An Assembly Line Container manufactures the Engine and Transmission independently, then installs (injects) them into the Car chassis during assembly.

Dimension Inversion of Control (IoC) Dependency Injection (DI)
Nature Abstract Design Principle / Architectural Paradigm Concrete Implementation Pattern
Primary Concern Who controls the execution flow and object lifecycles? How are dependent objects provided to a target component?
Alternative Implementations Service Locator Pattern, Template Method Pattern, Event Loops Constructor Injection, Setter Injection, Interface Injection

9. Complete Bean Lifecycle

The lifecycle of a Spring bean managed inside an ApplicationContext follows a strict execution path from birth to destruction.

Complete Lifecycle Execution Sequence

1
Instantiation: Constructor or factory method execution.
2
Populate Properties: Field and Setter dependency injection.
3
Aware Callbacks: Invokes BeanNameAware, BeanFactoryAware, ApplicationContextAware.
4
BeanPostProcessor (Pre-Init): postProcessBeforeInitialization() processes @PostConstruct.
5
InitializingBean: afterPropertiesSet() is invoked.
6
Custom Init Method: Configured initMethod executes.
7
BeanPostProcessor (Post-Init): postProcessAfterInitialization() generates AOP proxies.
8
Ready State: Bean is fully operational and cached.
9
PreDestroy Callback: @PreDestroy annotated methods execute on context shutdown.
10
DisposableBean: destroy() is invoked.
11
Custom Destroy Method: Configured destroyMethod executes.

10. Dependency Resolution Mechanism

When resolving injection points, Spring evaluates annotations, types, and qualifiers to locate candidate target beans.

Resolution Strategy Order
  1. Match by Exact Type: Container searches for candidate beans implementing the required type.
  2. Evaluate @Qualifier: If multiple beans exist, matches by explicit qualifier identifier.
  3. Evaluate @Primary: If no qualifier is specified, selects the bean marked with @Primary.
  4. Match by Name: Fallback match based on variable field or parameter name.
@Configuration
public class DatabaseConfig {
    @Bean @Primary
    public DataSource primaryDataSource() { return new HikariDataSource(); }

    @Bean @Qualifier("analytics")
    public DataSource analyticsDataSource() { return new HikariDataSource(); }
}

11. Circular Dependency & Three-Level Cache

A circular dependency occurs when Bean A depends on Bean B, and Bean B simultaneously depends on Bean A. While constructor-based circular dependencies cause unresolvable startup failures, setter/field injection circularities are resolved by Spring using a Three-Level Cache mechanism inside DefaultSingletonBeanRegistry.

The Three Cache Levels inside DefaultSingletonBeanRegistry

Cache Level Map Variable Name Description & Purpose
First-Level Cache singletonObjects Stores fully instantiated, injected, and initialized singleton beans ready for consumption.
Second-Level Cache earlySingletonObjects Stores early, un-initialized bean instances (raw objects created via constructor prior to property population).
Third-Level Cache singletonFactories Stores ObjectFactory<?> lambda factories capable of generating early AOP proxies for beans involved in circular loops.

Three-Level Cache Resolution Workflow

1
Spring attempts to instantiate Bean A. It puts an ObjectFactory for Bean A into the 3rd Level Cache (singletonFactories).
2
Spring populates Bean A's properties and discovers it needs Bean B.
3
Spring starts instantiating Bean B. It puts an ObjectFactory for Bean B into the 3rd Level Cache.
4
Spring populates Bean B's properties and discovers it needs Bean A.
5
Spring requests Bean A: Checks 1st Cache (Miss) → Checks 2nd Cache (Miss) → Checks 3rd Cache (Hit!).
6
Executes Bean A's ObjectFactory to get an early reference (or AOP proxy), moves Bean A to 2nd Level Cache (earlySingletonObjects), and removes it from the 3rd Cache.
7
Bean B receives the early reference of Bean A, completes its property population, initialization, and moves to the 1st Level Cache (singletonObjects).
8
Bean A now receives the fully initialized Bean B, completes its initialization, and moves to the 1st Level Cache.

12. Bean Scopes Deep Dive

Spring manages bean lifecycles across multiple predefined and custom scopes:

Scope Creation Policy Thread Safety Consideration
Singleton (Default) One instance per IoC container instance. Shared across all callers. Must be stateless or thread-safe.
Prototype New instance created upon every getBean() request or injection. Caller must manage cleanup; Spring does not execute destruction callbacks.
Request One instance per HTTP request lifecycle (Web ApplicationContext). Thread-confined to single request handling thread.
Session One instance per HTTP Session lifecycle. Must handle serialization if session state is replicated.
Application One instance per ServletContext scope. Shared across entire web application.

13. Lazy vs Eager Initialization

By default, the ApplicationContext eagerly instantiates all singleton beans during container startup to catch configuration errors early.

Eager Initialization (Default)

Pros: Fails fast at startup if configuration or dependencies are missing.

Cons: Increases initial application startup time and RAM consumption.

Lazy Initialization (@Lazy)

Pros: Faster startup and reduced initial memory footprint.

Cons: First HTTP request encountering lazy bean suffers latency; hides configuration errors until runtime.

14. Autowiring Modes

Legacy XML and explicit bean configurations support legacy autowiring modes prior to modern annotation scanning:

Mode Resolution Strategy
byName Matches property name with target bean identifier.
byType Matches property class type with container candidate bean type.
constructor Applies byType matching across constructor parameter arguments.
no / default Requires explicit manual <property> or <constructor-arg> declarations.

15. Bean Post Processor Mechanics

BeanPostProcessor interfaces allow custom extension of the Spring container by intercepting bean instances before and after initialization callbacks.

@Component
public class CustomLoggingPostProcessor implements BeanPostProcessor {
    
    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) {
        // Executes prior to @PostConstruct or initMethod
        return bean;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        // Used by Spring to construct Dynamic Proxies or CGLIB proxies (e.g., @Transactional)
        return bean;
    }
}

16. FactoryBean, ObjectFactory & Supplier

Spring provides specialized factory patterns for complex object creation:

Interface Primary Use Case
FactoryBean<T> Encapsulates complex custom instantiation logic (e.g. LocalSessionFactoryBean). Retrieving &beanName returns the factory itself; retrieving beanName returns the created object.
ObjectFactory<T> Encapsulates lazy lookup or prototype instantiation on demand inside singleton beans.
Supplier<T> Functional registration callback added in Spring 5 for programmatic bean definition registration.

17. @Component and Stereotype Annotations

Stereotype annotations meta-inherit from @Component to designate architectural layers:

@Component

Generic stereotype marker for utility components.

@Service

Business layer logic; transactional pointcut target.

@Repository

Data access layer; activates SQL exception translation.

@Controller / @RestController

Web layer; enables MVC mapping and JSON response serialization.

19. Internal Annotation Processing (ASM)

To maximize startup performance, Spring does not use Java reflection during component scanning. Instead, it processes .class files as raw byte streams using the ASM Bytecode Framework via SimpleMetadataReaderFactory. This allows Spring to evaluate annotation metadata without invoking the JVM ClassLoader.

20. Spring Boot Startup Flow

1
Execute main() → Invokes SpringApplication.run().
2
Deduces Environment type (Servlet Web vs Reactive vs Standalone).
3
Instantiates ApplicationContext (e.g. AnnotationConfigServletWebServerApplicationContext).
4
Executes Auto-Configuration import selectors (@EnableAutoConfiguration).
5
Performs Component Scanning and registers BeanDefinitions.
6
Instantiates singletons and starts embedded Web Server (Tomcat/Jetty).

21. Real Production Architecture Example

// 1. Repository Interface
public interface AccountRepository {
    Account findById(String id);
}

// 2. Repository Implementation (IoC managed)
@Repository
public class JpaAccountRepository implements AccountRepository {
    @Override
    public Account findById(String id) { return new Account(id, 500.00); }
}

// 3. Service Layer (Constructor DI)
@Service
public class AccountService {
    private final AccountRepository repository;

    public AccountService(AccountRepository repository) {
        this.repository = repository;
    }

    public Account getAccount(String id) { return repository.findById(id); }
}

// 4. Web Controller Layer
@RestController
@RequestMapping("/accounts")
public class AccountController {
    private final AccountService service;

    public AccountController(AccountService service) {
        this.service = service;
    }

    @GetMapping("/{id}")
    public ResponseEntity<Account> getAccount(@PathVariable String id) {
        return ResponseEntity.ok(service.getAccount(id));
    }
}

22. Internal Classes Reference

  • DefaultListableBeanFactory: Core implementation holding singleton maps and bean definition registries.
  • ConfigurationClassPostProcessor: Parses @Configuration classes and registers @Bean definitions.
  • AutowiredAnnotationBeanPostProcessor: Intercepts @Autowired and @Value annotations for injection.
  • ClassPathBeanDefinitionScanner: Scans packages for candidate components.

23. Performance Optimization & AOT

Modern Spring 6 / Spring Boot 3 introduces Ahead-Of-Time (AOT) compilation. Spring AOT pre-evaluates component scanning, bean definition registration, and proxy generation at compile time. This converts dynamic IoC operations into static C++ code when compiled with GraalVM Native Image, drastically reducing startup times to milliseconds and reducing memory usage.

24. Top 50 Interview Questions & Answers

Q1: How does Spring resolve circular dependencies in setter injection?
Via its Three-Level Cache inside DefaultSingletonBeanRegistry. It exposes an early un-initialized instance or AOP factory lambda (3rd level cache) before property population completes.
Q2: Why does constructor injection fail with circular dependencies?
Because a constructor must execute fully to produce an object reference. Spring cannot put an un-instantiated object reference into the early cache before constructor execution finishes.
Q3: Difference between ApplicationContext and BeanFactory?
ApplicationContext extends BeanFactory, adding eager loading of singletons, AOP support, event publication, i18n, and automatic post-processor registration.
Q4: What is a BeanDefinition?
An internal metadata object describing a bean's class, scope, dependencies, factory methods, and lifecycle callbacks.
Q5: How does @Autowired work internally?
Processed by AutowiredAnnotationBeanPostProcessor during the postProcessProperties lifecycle phase using reflection.
Q6: What is the default scope of a Spring bean?
Singleton.
Q7: How to inject a prototype bean into a singleton bean safely?
Using @Lookup method injection, ObjectProvider<T>, or proxyMode in @Scope.
Q8: What is the role of BeanPostProcessor?
Intercepts bean instances before and after initialization to wrap them in AOP proxies or process annotations.
Q9: Difference between @Bean and @Component?
@Component is class-level for automatic scanning. @Bean is method-level inside @Configuration for custom or 3rd-party object instantiation.
Q10: What is ASM in Spring?
A high-performance bytecode reading library used to scan class annotations without loading classes into the JVM ClassLoader.
Q11: What is the purpose of @Primary?
Gives precedence to a specific bean when multiple candidates match a dependency type.
Q12: What is the purpose of @Qualifier?
Narrows down matching candidate beans by specifying an explicit target bean identifier.
Q13: What happens if two singletons have a circular dependency in Constructor Injection?
Spring throws a BeanCurrentlyInCreationException during application startup.
Q14: How does @PostConstruct work?
Processed by CommonAnnotationBeanPostProcessor after property population and before custom init methods.
Q15: Does Spring manage the full lifecycle of prototype beans?
No. Spring instantiates and populates prototype beans, but does not execute destruction callbacks (e.g. @PreDestroy).
Q16: Difference between FactoryBean and BeanFactory?
BeanFactory is the IoC container interface. FactoryBean is a SPI interface implemented by user beans to construct complex instances.
Q17: What is the 1st level cache in Spring?
singletonObjects map holding fully ready singleton instances.
Q18: What is the 2nd level cache in Spring?
earlySingletonObjects map holding raw, un-initialized early bean references.
Q19: What is the 3rd level cache in Spring?
singletonFactories map holding ObjectFactory lambdas for generating early AOP proxies.
Q20: Why does Field Injection hinder unit testing?
Because dependencies cannot be passed without using reflection or launching a full Spring container runner.
Q21: Can we mark a @Bean method static?
Yes. Static @Bean methods run without instantiating their declaring @Configuration class early.
Q22: What is @Lazy?
Defers bean instantiation until explicit runtime access.
Q23: How to handle optional dependencies in Spring?
Using Java Optional<T>, @Autowired(required = false), or ObjectProvider<T>.
Q24: What is ConfigurationClassPostProcessor?
A BeanFactoryPostProcessor that parses @Configuration classes and registers @Bean definitions.
Q25: Difference between @Repository and @Component?
@Repository meta-inherits from @Component and adds automated SQL exception translation.
Q26: How does Spring resolve Collection injection?
Injects all candidate beans matching the element type into a List<T> or Map<String, T>.
Q27: What is Method Injection?
Using @Lookup on an abstract method to fetch a prototype bean dynamically inside a singleton.
Q28: What is BeanDefinitionRegistry?
An interface providing methods to register, remove, and inspect BeanDefinition instances.
Q29: Difference between DisposableBean and @PreDestroy?
@PreDestroy is annotation-based (JSR-250); DisposableBean requires implementing Spring's destroy() interface.
Q30: How to inject primitive values from properties files?
Using @Value("${property.name}").
Q31: What is Spring AOT?
Ahead-of-Time compilation performing component scanning and proxy generation at build time.
Q32: What happens if multiple beans match @Autowired without @Qualifier or @Primary?
Spring throws a NoUniqueBeanDefinitionException during resolution.
Q33: Can we inject ApplicationContext into a bean?
Yes, by implementing ApplicationContextAware or autowiring ApplicationContext.
Q34: What is ObjectFactory?
A factory interface for lazy or on-demand retrieval of managed beans.
Q35: Is Singleton bean thread-safe by default?
No. Thread safety depends on whether the class implementation is stateless or synchronized.
Q36: Difference between byName and byType autowiring?
byName matches bean ID to variable name; byType matches candidate class type.
Q37: What is @SpringBootApplication composed of?
@SpringBootConfiguration, @EnableAutoConfiguration, and @ComponentScan.
Q38: Why does Spring default to Constructor Injection?
Enforces immutability, prevents null pointers, and detects circular dependencies early.
Q39: What is the purpose of @Order?
Defines execution order for post-processors or collection bean injections.
Q40: Difference between InitializingBean and @PostConstruct?
@PostConstruct runs first via BeanPostProcessor; InitializingBean is an interface execution.
Q41: What is @Scope(proxyMode = ScopedProxyMode.TARGET_CLASS)?
Generates a CGLIB proxy allowing short-lived scoped beans (e.g. Request) to be injected into singletons.
Q42: What is BeanCurrentlyInCreationException?
An exception thrown when Spring detects an unresolvable circular constructor reference.
Q43: What is DefaultListableBeanFactory?
The default full-featured BeanFactory implementation inside Spring.
Q44: Can we use @Resource instead of @Autowired?
Yes. @Resource (Jakarta EE) matches by name first, then by type.
Q45: How to trigger context shutdown in standalone apps?
By invoking context.registerShutdownHook().
Q46: What is PropertySourcesPlaceholderConfigurer?
A BeanFactoryPostProcessor that resolves ${...} property placeholders in bean definitions.
Q47: Difference between @Profile and @Conditional?
@Profile is a specialized subset of @Conditional for environment toggling.
Q48: Can a @Bean method be private?
No. @Bean methods must be overridable/accessible by container invocation logic.
Q49: What is @EventListener?
Annotation to listen for ApplicationContext published events asynchronously or synchronously.
Q50: Why is IoC beneficial for enterprise software?
Decouples configuration from code, enforces clean layer separation, enables unit testing, and automates lifecycles.

25. Common Mistakes

1. Using Field Injection (@Autowired on private fields): Prevents immutability and hides dependencies. Use Constructor Injection.
2. Mutating State inside Singleton Beans: Singleton beans are shared across threads. Adding non-thread-safe instance fields causes severe race conditions.
3. Relying on Prototype Scope for Cleanup: Spring does not run @PreDestroy on prototype beans. Callers must destroy prototype instances manually.

26. Best Practices

  • Constructor Injection Always: Mark injected dependencies private final.
  • Favour Interface Abstractions: Inject interface types (e.g. OrderRepository) rather than concrete implementations (JpaOrderRepository).
  • Keep Configuration Classes Stateless: Declare @Bean methods as pure factory setups.

27. Cheatsheet

IoC: Architectural principle inverting control of object lifecycles.

DI: Pattern executing dependency wiring via constructors, setters, or fields.

BeanDefinition: Metadata holder describing target beans before instantiation.

3-Level Cache: Resolves setter circular dependencies (singletonObjects, earlySingletonObjects, singletonFactories).
