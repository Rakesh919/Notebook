Spring Framework · Core Architecture

Stereotypes & @Bean

How Spring discovers your classes, organizes them into layered enterprise architectures, and wires both internal components and third-party tools into the IoC container.

1. What are Stereotype Annotations?

Stereotypes are marker annotations placed on top of classes. When Spring starts up, its component scanner locates these annotations, instantiates the classes, and manages them as beans inside the container.

The Core Rule: Under the hood, @Service, @Repository, and @Controller are all meta-annotated with @Component. Any of them will register a bean, but their specialized names communicate clear architectural intent to developers and provide specific runtime behaviors to Spring.

2. Visual: The 3-Tier Layered Architecture

Spring stereotypes match standard enterprise application layers. Each layer has a single responsibility and only talks to the layer directly below it:

3. The Core Stereotype Family

@Component

Generic stereotype for utility beans, background listeners, or any Spring-managed class that doesn't fit a specific layer.

@Service

Business logic layer. The primary target for @Transactional boundaries and domain workflows.

@Repository

Data access (DAO) layer. Automatically catches driver-specific exceptions (like SQL/Hibernate) and translates them into Spring's DataAccessException.

@RestController

Web layer. Combines @Controller and @ResponseBody to return raw data (usually JSON) instead of HTML templates.

4. What is @Bean and Why Do We Need It?

If @Component automatically detects classes, why does @Bean exist? The answer comes down to source code ownership and configuration complexity.

Visual Comparison: Registration Mechanisms 
 1. @Component (Automatic Scanning)
    ┌───────────────────────────┐
    │ @Service                  │ ──> Spring automatically finds your file
    │ public class OrderService │     and calls its constructor.
    └───────────────────────────┘     (Requires editable source code)

 2. @Bean (Explicit Factory Registration)
    ┌───────────────────────────┐
    │ @Configuration            │
    │ public class AppConfig {  │
    │   @Bean                   │ ──> You write the exact creation logic.
    │   public RestTemplate rt(){     Essential for 3rd-party JARs where
    │     return new ...;       │     you cannot add @Component!
    │   }                       │
    │ }                         │
    └───────────────────────────┘

5. @Configuration: Full vs Lite Mode

Methods annotated with @Bean live inside classes. How you annotate the parent class changes how Spring handles singleton guarantees:

@Configuration (Full Mode)

Spring wraps the class in a CGLIB proxy. If one @Bean method calls another @Bean method internally, the proxy intercepts it to return the cached singleton rather than creating a duplicate object.

@Component (Lite Mode)

No CGLIB proxy is generated. Calling an inter-bean method directly executes standard Java code, instantiating a new unmanaged object every time.

@Configuration
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    public UserService userService() {
        // CGLIB intercepts this call: returns the singleton PasswordEncoder bean!
        return new UserService(passwordEncoder()); 
    }
}

6. Clean Production Code Example

How the entire flow wires together cleanly without messy configuration:

// 1. Controller receives HTTP request
@RestController
@RequestMapping("/api/orders")
public class OrderController {
    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping
    public ResponseEntity<Order> placeOrder(@RequestBody OrderDto dto) {
        return ResponseEntity.ok(orderService.createOrder(dto));
    }
}

// 2. Service processes business rules inside transaction
@Service
public class OrderService {
    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    @Transactional
    public Order createOrder(OrderDto dto) {
        // Business logic here
        return orderRepository.save(new Order(dto.getItem()));
    }
}

// 3. Configuration registers third-party external tool
@Configuration
public class NetworkConfig {
    @Bean
    public RestTemplate restTemplate() {
        return new RestTemplate();
    }
}

7. Common Pitfalls

1. Putting @Component Everywhere: Don't mark everything as a generic component. You lose automated exception handling on repositories and clear architectural boundaries for AOP pointcuts.
2. Storing Mutable State in Singletons: All stereotype beans are singletons by default. Never store request-specific user data in instance variables—incoming threads will overwrite each other's data.
3. Package Scanning Mismatches: Spring Boot scans everything under the package containing your main @SpringBootApplication class. If you put classes in an external package, Spring won't discover them without an explicit scanBasePackages declaration.

8. Quick Summary

  • Use @RestController for REST APIs (JSON response bodies).
  • Use @Service for business logic and @Transactional boundaries.
  • Use @Repository for data access to enable automatic persistence exception translation.
  • Use @Bean inside @Configuration classes whenever configuring third-party libraries or complex custom setups.
