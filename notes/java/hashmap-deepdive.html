Everything below is correct. Two small refinements are flagged inline.

✔HashMap stores data in key-value pairs. Keys must be unique; values can be duplicated.
✔Exactly one null key is allowed.
✔Internally it's an array of buckets. Each bucket is a linked list of nodes storing [hash, key, value, next].
✔map.put("code", 1) — the key is converted to a hash, then to a bucket index (say 14), and the entry is stored at buckets[14].
✔A single bucket can hold more than one element (a collision chain).
✔Searching converts the key to the same bucket index, then compares keys inside that one bucket only — not the whole map. Refinement: the comparison is hash-first, then .equals() — it checks the cheap stored hash int before ever calling .equals() on the key.
✔Different keys can share the same hash code and end up in the same bucket. One addition: if a single bucket's chain grows to 8+ entries (and table capacity ≥ 64), Java converts that bucket from a linked list into a red-black tree so the worst case is O(log n), not O(n).
A

Core properties

Unique keys

Putting an existing key overwrites its value instead of adding a new entry. Uniqueness is enforced via hashCode() + equals().

Duplicate values allowed

Many different keys can map to the identical value object — no uniqueness constraint on values.

One null key

Exactly one entry may have a null key. Java special-cases it to always live in bucket 0 (see further down).

Multiple null values

Any number of keys may map to a null value — that's unrelated to the null-key rule.

No ordering guarantee

Iteration order depends on bucket layout and resizing history, not insertion order. (Use LinkedHashMap if you need insertion order.)

Not thread-safe

Concurrent put()s from multiple threads can corrupt the bucket structure. Use ConcurrentHashMap instead.

The backing field is Node<K,V>[] table. Each Node carries four fields — this is the unit that gets created, compared, and chained.

E

Inside a collision: bucket 14 as a linked list

"Aa" and "BB" hash to the same bucket. Both nodes coexist, chained by next.

Why both fit: same hash, different keys. hashCode() only has ~4.3 billion possible outputs; infinitely many keys exist, so collisions are mathematically guaranteed eventually — this is normal, expected behavior, not a bug.
F

get("BB") — step by step

1  Compute hash from the key, then index = hash & (capacity-1). Jump straight to buckets[index] — O(1).
2  Is buckets[index] empty?
YESKey isn't in the map. Return null immediately.
NOWalk the chain (or tree, if treeified). For each node:
2a  Does stored hash match?
NOSkip immediately — definitely not this node. Move to next.
YESHash matched — now actually call .equals(key).
2b  .equals() true?
YESFound it. Return this node's value.
NOFalse alarm (different key, same hash) — keep walking the chain.
3  Reached the end of the chain with no match → return null.
Only the entries inside one bucket are ever compared — never the whole map. With a good hash function and load factor 0.75, that's usually 0 or 1 comparisons.
G

When a bucket overflows: list → red-black tree

At TREEIFY_THRESHOLD = 8 entries in one bucket (and table capacity ≥ 64), that bucket converts from a linked list to a tree — worst case becomes O(log n) instead of O(n).

red node black node
If removals shrink the chain back to 6 entries, it converts back to a plain linked list — trees cost more memory, not worth keeping for a small bucket. This treeify path mainly defends against pathological cases (e.g. someone deliberately crafting many keys with identical hashes).
H

Resizing: when the whole table grows

Default capacity is 16, default load factor is 0.75. Once size > capacity × loadFactor (e.g. 13th entry in a 16-bucket table), the entire table doubles and every existing node gets rehashed into the new array.

before — capacity 16, 13 entries (over the 12-entry threshold)
↓ capacity × 2, rehash every node ↓
after — capacity 32, same 13 entries, spread thinner
This is why occasional put() calls are slower than others — that's a resize happening. Capacity always doubles (never grows by 1), which keeps the amortized cost of insertion at O(1) even though individual resize operations are O(n).
I

The null key special case

You can't call null.hashCode() — it would throw a NullPointerException. So HashMap special-cases it.

The null key always lives in bucket 0. Uniqueness is still enforced exactly like any other key — put(null, x) twice overwrites the same entry, it doesn't create two.
